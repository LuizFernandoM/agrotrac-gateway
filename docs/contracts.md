# Gateway e autenticação do MVP — retomada de 17/11/2026

Contrato de implementação. Os sete módulos mantêm repositórios e responsabilidades próprios: Infra, Core, Audit, Live, Gateway, Web e Mobile. Core decide capacidade, janelas e reservas. Audit decide sincronização, replay e histórico. Live mantém projeção e WebSocket e passa a ser a autoridade de sessões. Gateway aplica a política de acesso e encaminha requisições. Web e Mobile consomem a mesma API. O aceite Live está em reverificação independente. O checkpoint registra offline e persistência no iPhone como aprovados por relato e sincronização física pelo Gateway como pendente.

## Revisão vinculante da coordenação — 17/11/2026

- Aprovação para implementar código e testes isolados Gateway/Web; não é aceite do sistema nem autorização para provisionar credenciais reais ou expor portas externas. Live tem outro executor corrigindo AMQP: não alterar seus arquivos ou iniciar segundo escritor nele. Autenticação Live será delegada após essa entrega. Todos os requisitos de auth e TLS permanecem no escopo.
- Endpoint de verificação interna fixado em `GET /internal/auth/verify`. Nginx location `= /_agrotrac_auth` é `internal` e encaminha sem corpo ao Live, sobrescrevendo `X-Original-Method`, `X-Original-URI` (caminho canônico SEM query), `X-Forwarded-For` com endereço observado e `X-Forwarded-Proto` com protocolo do Gateway. Nunca encaminhar `/internal/*` externamente. Live valida método/caminho pela mesma allowlist; ausência de metadados válidos falha fechada. Cabeçalhos de identidade do cliente não são confiáveis. Não confiar em cadeias X-Forwarded-* fornecidas pelo cliente.
- Verificador retorna 204 com `X-Agrotrac-User-Id` e `X-Agrotrac-Role`, ou 401/403; indisponibilidade retorna 503 e é tratada fechada pelo Gateway. Core/Audit não precisam receber identidade nesta entrega; remover Authorization, Cookie, X-CSRF-Token e cabeçalhos de identidade antes desses upstreams. Rotas auth preservam credenciais para o Live; upgrade WS também precisa Cookie/Origin para dupla validação. Código AUTH inexistente não pode ser substituído por autorização incondicional em configuração de produto.
- Cabeçalhos de correlação são `X-Correlation-Id`, UUID v4 validado/gerado no serviço; Gateway não deve quebrar geração/validação do upstream. Login: JSON no máximo16KiB; APIs JSON64KiB; upload12MiB, por rota. Metadados/corpos/tokens e query não entram em logs. Arquivo de usuários aceita somente hash Argon2id real; fixtures isoladas não são contas padrão do produto.
- Login Web retorna objeto direto `{user:{id,role},expires_at,csrf_token}` e cookie; Mobile objeto direto `{user:{id,role},expires_at,access_token,token_type:'Bearer'}`. `GET /v1/live/auth/session` retorna sessão e csrf para Web. Falha401 não apaga dados offline e não é login anônimo. Expiração absoluta8h default configurável validado. Permissões operator/admin são as da tabela; sem novos perfis/CRUD ou token estático.
- Autorizada criação de perfis/Compose/configuração opt-in e documentação em arquivos novos, preservando compose/env/volumes existentes. A aplicação da configuração integrada com nomes/portas/mounts/novas credenciais reais fica para revisão concreta da coordenação; não usar automaticamente os dados existentes para inicializar outra infraestrutura. Testes locais com containers/redes/portas loopback efêmeros e credenciais fixture geradas somente para esse teste são autorizados, sem removê-los depois; registrar recursos e fechá-los sem apagar dados. Não abrir bind público nem firewall.
- Os backends mantêm defaults locais seguros. Suporte futuro a perfil container explícito precisa ser implementado pelo dono de cada módulo; não editar silenciosamente Core/Audit/Live no executor Gateway. Fixtures HTTP/WS/auth em testes Gateway comprovam proxy/política e NÃO a implementação real de sessão Live. Relatório distingue essa etapa da integração com serviços reais, que continua obrigatória antes do aceite final.
- Web usa somente URL pública/configurável Gateway; Vite dev proxy pode encaminhar a API e WS ao mesmo Gateway local sem expor upstreams. Origem de teste é explicitamente permitida pela config fixture de auth, não por wildcard. Não guardar token/CSRF/senha no localStorage ou persistir senha; WS browser com cookie+Origin e subprotocolo. UI deve mostrar indisponibilidade real se Gateway/auth não estiverem disponíveis, não dados mock como se fossem reais.

## Rotas e política de acesso

| Requisição canônica | Upstream | Permissão |
|---|---|---|
| GET /v1/core/silos[/ID], /v1/core/windows[/ID], /v1/core/bookings[/ID] | agrotrac-core:3001 | operador ou admin |
| POST /v1/core/bookings, DELETE /v1/core/bookings/ID | Core | operador ou admin |
| POST /v1/core/silos, POST /v1/core/windows, PATCH /v1/core/windows/ID/status | Core | admin |
| POST /v1/audit/weighings/sync | agrotrac-audit:3003 | operador ou admin |
| GET /v1/audit/weighings, /v1/audit/weighings/ID/romaneio | Audit | operador ou admin |
| GET /v1/audit/events | Audit | admin |
| GET /v1/live/snapshot e GET /live com upgrade | agrotrac-live:3002 | operador ou admin |
| POST /v1/live/auth/login | Live | sem sessão, com controles abaixo |
| GET /v1/live/auth/session, POST /v1/live/auth/logout | Live | sessão válida, logout com proteção de mutação |
| GET /health/live e GET /health/ready | Gateway e prontidão do Live | públicos, GET exato, limitados e resposta sanitizada |

Publicar somente método e caminho da tabela, usando correspondência exata ou expressões ancoradas para IDs no formato aceito pelo serviço. Rotas desconhecidas retornam 404 e métodos divergentes em caminhos conhecidos retornam 405. Esse inventário também é a política do verificador Live. Nginx classifica a URI original separada da query antes de encaminhar. Recusar no caminho escapes percentuais, barras repetidas ou invertidas, segmentos ponto e barra final de API. Preservar a query original para o serviço e excluir query dos logs. Normalização do Nginx por si só é insuficiente para autorizar. As exceções públicas passam pela mesma validação e são restritas aos métodos declarados. A Web recebe fallback SPA apenas nas rotas de UI registradas, fora das famílias API, WS, health e internas. Ferramentas administrativas, quarentena e health por serviço ficam na rede privada.

Usar proxy_pass sem componente URI nem barra adicional no destino, preservando /v1/core, /v1/audit, /v1/live e /live. Não habilitar retry automático de mutações, especialmente POST de reserva. Proxy preserva status, query, corpo e cabeçalhos de contrato e correlação, com limite e sanitização do identificador. Validar Host e sobrescrever metadados encaminhados com valores do Gateway. Ignorar cabeçalhos de identidade enviados pelo cliente e remover credenciais de sessão/CSRF antes de encaminhar a Core e Audit.

Aplicar auth_request em todas as rotas de negócio, inclusive upgrade. Um location interno exato envia ao Live um subrequest sem corpo, com método e caminho canônico originais sobrescritos pelo Gateway, Cookie ou Authorization, Origin e X-CSRF-Token quando aplicáveis. O endpoint de verificação é interno no Live e inacessível pelo roteamento externo, mesmo por alias. O Live retorna 204, 401 ou 403, autorizando método e caminho por lista positiva. Falha de conexão, prazo ou dependência do verificador fecha o acesso. Como auth_request converte status inesperados em erro interno, mapear esse erro para 503 na borda sem reclassificar erros de negócio dos upstreams. Core e Audit recebem tráfego apenas pela rede privada da integração.

## Sessões e contrato para Web e Mobile

Usar usuários provisionados com ID opaco estável, identificador de login, papel operator/admin e hash Argon2id com salt individual e parâmetros revisados. Carregar arquivo local fora do Git via caminho de configuração, montado somente leitura e com permissões restritas. Validar schema e rejeitar inicialização com configuração inválida. Templates levam somente nomes e caminhos. Fixtures de integração usam hashes reais em ambiente isolado, sem fallback guest ou credenciais de infraestrutura. Os identificadores reais, responsáveis pelo provisionamento e rotação e forma de colocar os hashes no host são decisões da coordenação. Solicitar novas credenciais apenas quando o fluxo concreto de configuração estiver pronto. A matriz é a proposta mínima para um ambiente compartilhado, sem perfil motorista adicional, CRUD de papéis ou premissa de segregação por organização.

- POST /v1/live/auth/login aceita JSON { username, password, client: "web" | "mobile" }. Web exige Origin exata e recebe 200 { user: { id, role }, expires_at, csrf_token } e cookie de sessão. Mobile nativo recebe 200 { user: { id, role }, expires_at, access_token, token_type: "Bearer" }; rejeitar Origin de navegador no modo mobile e manter CORS fechado. Credencial inválida recebe 401 genérico, formato inválido 400 e excesso 429 com Retry-After. Limitar login no Gateway por IP e no Live por conta normalizada e IP confiável, inclusive tentativas para contas inexistentes. Dependência indisponível retorna 503. Limitar tamanho da senha antes do hash e executar verificação de custo comparável para identificador desconhecido.
- GET /v1/live/auth/session retorna 200 com user e expires_at, mais csrf_token para cookie Web. Sessão ausente, expirada ou revogada recebe 401. POST /v1/live/auth/logout retorna 204 após revogação e apaga o cookie com os mesmos atributos de escopo. Todas as respostas de auth usam Cache-Control: no-store. Erros de auth e indisponibilidade do Gateway usam JSON { error: { code } } com UNAUTHENTICATED, FORBIDDEN ou SERVICE_UNAVAILABLE conforme o status. Bearer inválido recebe também WWW-Authenticate: Bearer. Preservar envelopes e códigos dos serviços de negócio.
- Gerar token opaco com 32 bytes aleatórios criptográficos. Indexar sessão Redis por SHA-256 do token em namespace próprio, guardar sujeito, papel, modo e vencimento, com TTL absoluto proposto de 8 horas e sem renovação implícita. Rejeitar Cookie e Bearer simultâneos. Logout invalida registro antes de confirmar. Expiração e revogação invalidam HTTP e sockets. Rotação/revogação administrativa de credencial deve invalidar sessões correspondentes por versão de credencial ou operação interna explícita. Nunca registrar senha, Cookie, Authorization, token, CSRF ou corpo de login.
- Cookie final __Host-agrotrac_session, HttpOnly, Secure, SameSite=Lax, Path=/ e sem Domain. O estágio de integração HTTP em loopback usa nome distinto e fixture isolada. Web guarda CSRF em memória e recupera em /auth/session (sob /v1/live). Mutações autenticadas por cookie exigem Origin exata e X-CSRF-Token vinculado à sessão em comparação constante. Login Web exige Origin exata e JSON para evitar CSRF de login. Mobile usa Authorization em cada sync de Audit, sem depender de cookies Expo Go. Na expiração conserva fila e fotos locais e aguarda login antes da próxima tentativa.
- Web interpreta 401 como retorno ao login e 403 como ação indisponível com sessão preservada. Em 503, indica indisponibilidade. O dashboard abre /live em mesma origem com o subprotocolo agrotrac.live.v1 e usa snapshot inicial, atualizações, checkpoint e resync do contrato Live, com backoff e jitter. Não há polling REST. O browser envia cookie no upgrade e Live valida a sessão e Origin contra lista explícita de esquema, host e porta. O upgrade de navegador sem Origin ou com Origin divergente falha. Nesta entrega Mobile usa somente REST. Não transmitir credenciais na URL, subprotocolo ou localStorage.
- Live associa cada socket ao hash da sessão, valida antes do 101 e antes de processar resync, fecha em logout e no prazo de expiração. Em mais de uma instância combinar notificação Redis com revalidação em cada heartbeat para cobrir perda do aviso. Falha de validação encerra o socket e impede novas entregas. Usar 1008 para sessão inválida após upgrade e manter códigos de prontidão e protocolo do Live.

Recomendação para eventos de sessão: publicar agrotrac.live.session.started e agrotrac.live.session.ended em agrotrac.events com o envelope existente e binding compatível do Audit, IDs estáveis, sessão como agregado opaco, versões 1/2 e motivo enumerado de encerramento. Payload sem login, IP, token, hash de token ou PII. Para publicação confiável, gravar mudança de sessão e registro pendente atomicamente no Redis, com índice de vencimentos para gerar encerramento inclusive por expiração sem depender de notificações voláteis. Drenar com canal de publisher confirms, mandatory e mensagem persistente, retirar pendência após confirmação roteada e repetir com o mesmo event_id. Audit deduplica por event_id. Usar armazenamento e durabilidade Redis aprovados pela coordenação e explicitar que a garantia depende dessa durabilidade. Antes de habilitar, verificar binding, envelope, reconciliação e redelivery. Sem banco novo no Live.

## Limites e integração local

- Permitir apenas em /v1/audit/weighings/sync teto Nginx de 12 MiB para multipart. Audit continua aplicando 10 MiB para foto e 64 KiB para JSON e suas regras de partes, replay e conteúdo. Aplicar 64 KiB de teto a JSON nas demais rotas, com limite menor em login. Preservar Content-Type com boundary e erros de aplicação. Buffer de requisição e temporários limitados, com corpo ocioso de até 30 s.
- Proxy WS usa HTTP/1.1, Upgrade, Connection mapeado e Sec-WebSocket-Protocol preservado nos dois sentidos. Sem buffering/cache no canal. Prazo ocioso de 45 s supera ping de 15 s mais prazo de pong de 10 s. Manter checkpoint Live de 10 s e detecção do cliente em 20 s. Sugestão inicial de conexão 2 s e leitura 8 s em auth/REST, com 30 s em sync. Readiness pública encaminha somente /health/ready do Live, com prazo curto, resposta sanitizada e 503 quando Live não está READY. A prova de prontidão de Core e Audit fica nos checks privados do Compose e nos testes de integração; liveness pública indica apenas o processo Gateway. Passar 503 do Live em snapshot/upgrade e traduzir falha de conexão ou timeout do Gateway em 503 sanitizado.
- A máquina tem Docker Desktop e docker.exe. WSL lista docker-desktop, e nginx.exe não foi encontrado no PATH. Usar Docker Compose com projeto de integração isolado, DNS por nome de serviço e versões fixadas, incluindo Nginx com módulo http_auth_request confirmado em nginx -V. Nginx em container não alcança os listeners 127.0.0.1 de Windows via host.docker.internal. Core, Audit e Live ganham perfil explícito para bind 0.0.0.0 dentro de containers sem ports publicados. Configurar Core interno para Live pelo DNS da rede privada. Web entrega estáticos pelo próprio Nginx.
- Coordenação integra pela Infra um Compose opt-in em projeto separado, usando contextos Git irmãos, rede privada e dependências PostgreSQL, Redis e RabbitMQ próprias do perfil com volumes próprios e portas internas. O único port publicado para o estágio local é Gateway em 127.0.0.1 com porta escolhida após checagem de conflito. Aplicar migrations no ambiente de integração antes de liberar readiness e provisionar credenciais via configuração ignorada com fixtures. Reproduzir a partir das mesmas revisões, versões, comandos Compose e perfis documentados. A coordenação aprova nomes, portas, binds, redes, volumes, mounts, credenciais e qualquer reuso de dependências existentes. HTTP local é estágio de teste. Aceite final requer HTTPS/WSS e origem/certificado confiáveis. Teste iPhone por endpoint alcançável requer autorização separada antes de exposição externa.

## Aceite e ownership

1. Gateway executa nginx -V e nginx -t na imagem real e sobe a integração de loopback. Exercitar allowlist e status com namespace, trailing slash, double slash, encoding, rota interna, métodos e cabeçalhos forjados. Confirmar ausência de publicação direta dos upstreams.
2. Core via Gateway com fixture de operador testa reserva HTTP e race de capacidade com concorrentes distintos. Preservar resultado de negócio e verificar que 401/403 não produzem mutação. Audit via proxy testa sync multipart com foto de 10 MiB, criação 201, replay 200 e conflito 409. Cobrir JSON e foto no limite e acima, multipart total acima do teto e boundary ausente ou inválido.
3. Live via proxy com dois clientes autenticados exige 101, subprotocolo correto, snapshot e atualização para ambos, reconnect/resync e heartbeat. Cobrir 401 sem sessão, login válido, 403 por papel, Origin incorreta, CSRF ausente ou inválido, revogação de socket, expiração e 503 em indisponibilidade, readiness e timeout. Web valida login, restauração, logout, estados de erro e ausência de polling.
4. Executar backends com schemas, namespaces, filas/vhost e armazenamentos isolados. Preservar fixtures e dados com identificadores únicos e expiração natural, sem DROP, TRUNCATE, FLUSH, DEL de limpeza, purge ou alteração global de configuração. A revogação de uma sessão sob teste é comportamento funcional. Registrar observações e comandos efetivamente executados. Esta entrega é arquitetura e os testes acima estão pendentes.

Gateway executor escreve apenas configuração, imagem e documentação do Gateway. Live auth executor escreve apenas Live, incluindo credenciais, sessões, verificador e upgrade. Web executor escreve apenas Web e pode avançar pelo contrato e fixtures antes da configuração real. Coordenação/Infra define integração e aplica configuração sensível após revisão. A ligação do Mobile à sessão Bearer e o teste físico ficam em tarefa própria. O aceite independente do Live e a aprovação TLS/exposição seguem seus fluxos existentes.
